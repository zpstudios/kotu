## A439 다중 스킨 사용 철회와 원래 디자인 복원

2026-11-26 사용자는 여러 스킨 제공을 철회했다. 이미 구현한 디자인은 삭제하지 않고 제품에서 사용하지 않도록 한다. 스킨 전환을 도입하며 바꾼 구조와 호출 경로를 이전 버전과 대조하고, UI가 크게 느려졌다는 제보의 원인을 조사·수정한다. 래퍼 계층의 존재만으로 원인이라고 단정하지 않으며 코드상 비용과 실제 측정을 구분한다.

복원 기준은 원래 디자인의 테마와 상호작용이다. 버튼 등 조작부의 통일성 정리는 유지하고, 그 정리 이전의 코드·배치로 통째로 되돌리지 않는다. 현재 첫 번째 Original만 남기는 것으로도 충족하지 않는다. 사용자는 원래 메뉴에서 모듈명에 마우스를 올릴 때 보이던 그림자 같은 호버 표시가 일부 스킨에는 있으나 Original에는 빠졌다고 제보했다. 도입 전 구현·실제 화면과 비교해 이 표시 및 다른 누락 동작을 복원한다.

현재 선택 ID 등 기존 설정과 구현 자료는 보존한다. 비활성화한 런타임 경로, 성능 조사·측정과 복원한 시각 상태는 아래에 기록한다. A438 검색은 v0.435.0으로 공식 배포·설치했으며 A439와 제품 변경·배포 단위를 구분한다. [진행 범위](../../REQUIREMENTS.md#open-work) · [사용자 원요구](../../history/requirements-completed-index.md#a439)

### 2026-11-27 후속 재확인

사용자는 “메뉴 호버도 원래 수준으로 되돌려주고. 속도 문제도 해결하자.”고 요청하며, 과거·현재 버전을 직접 사용해 차이를 확인하는 방법과 프로그래밍적 차이에서 원인을 찾는 방법을 제시했다. 같은 A439의 계속 작업으로 두 접근을 함께 적용한다. 스킨 도입 전 실제 기준 버전과 v0.436.0에서 설정·자료·화면 크기·동작을 맞춰 비교하고, 재현한 긴 대기 구간을 코드 경로와 연결해 수정한다. 기존 v0.435.0 Original과 후보 비교를 도입 전 제품의 직접 비교로 바꾸어 부르지 않는다.

후속 제보에 따라 계측 없는 v0.436.0 검수본의 라이트 메뉴를 다시 열었다. 모듈 항목 강조가 매우 약했으므로 원래 수준으로 충분히 복원됐다는 판정은 정정한다. `artifacts/a439-review/product-light-menu-recheck-normal.png`·`product-light-menu-recheck-hover.png`는 메뉴 표시와 Archive 우클릭 후 포인터가 놓인 상태다. 순수 호버 입력 실험은 아니며 자동화 커서의 파란 효과를 제품 그림자로 세지 않는다. 원래 효과가 실제 DropShadow라는 요구도 발명하지 않는다. 검수본을 정상 종료하고 Test 원본 28키를 바이트 복원했으며 공식 앱은 조작하지 않았다. 다크 시작의 기존 관측은 유지하되 라이트의 충분한 강조나 전체 체감 속도 해결을 대신하지 않는다.

### 도입 전 소스 재구성과 후속 측정

2026-11-27 도입 직전 `f74a2896107075c083883e1ff022e671e11b3e42`(v0.432.2)와 v0.436.0 소스를 별도 Test 앱으로 실행했다. 둘 다 현재 복원한 같은 WinUI DLL을 사용했으므로 과거 공식 배포 바이너리 그대로의 비교는 아니다. 라이트·시스템 기본 앱 배율·실제 709×535 창·같은 TXT 480개 자료와 설정을 사용했다. 폴더 열기·600 아래/위 스크롤·상위 복귀·재방문의 동작 수와 순서는 맞췄으나 요청 간격·총시간은 다르며 캐시는 지우지 않았다.

이후 v0.432.2 공개 Full을 별도로 내려받아 공개 SHA-256과 대조했다. 공식 제품 커밋 `d87dc7db79a8674fdd2799874c0587523d269c63`과 재구성 기준 사이의 제품 소스 차이는 없었고 공식 WinUI DLL도 현재 검수본과 같은 해시였다. 이 비교에서 부동 의존성이 WinUI 바이너리 차이를 만들었다는 가설은 뒷받침되지 않는다. 보호 보존본의 캐시 패키지는 공개 Full과 같지 않았으므로 별도 다운로드 검증과 구분한다. 근거는 `artifacts/a439-followup/preskin-official/verification.json`이며, 재구성 Test 앱의 조작을 과거 공식 실행 파일 자체의 조작으로 바꾸어 부르지 않는다.

새 계측을 넣기 전 기존 `NavDiagnostics`로 본 폴더 레이아웃 구간은 현재 229/248ms, 도입 전 136/276ms였다. 반복에서 순서가 뒤집혔으며 스크롤 후 최장 heartbeat 간격도 양쪽 모두 약 2.6초였다. 이 값은 물리 입력부터 화면 표시까지의 시간이나 전체 UI 정지의 직접 증명이 아니다. 같은 의존성으로 재구성한 도입 전 라이트 메뉴도 강조가 약했다. 현재 일반 Button의 흰색 계열 hover와 밝은 팝업 배경의 대비를 별도로 다룬다.

그 뒤 두 단계 복사본에만 같은 제한된 메서드·입력·Rendering 콜백 계측을 넣었다. 도입 전/현재의 최장 Rendering 콜백 간격은 약 2.73/2.62초였으며 각각 2초 이상 간격이 12회였다. 현재 추가 오버레이 크기 처리의 최대 한 호출은 약 58ms이고 긴 간격은 해당 처리 밖에서도 나타났다. 유휴·포인터를 빈 정보 패널에 둔 조건에서도 긴 간격이 남았다. 오버레이 처리가 긴 지연의 원인이라는 가설은 이 자료로 뒷받침되지 않는다. 중첩 메서드 시간은 합산하지 않으며 콜백 간격을 GPU 표시 시간으로 바꾸어 부르지 않는다.

초기 관리 코드 CPU 표본은 대부분 WinUI 네이티브 진입의 `UNMANAGED_CODE_TIME`으로 남아 실제 네이티브 원인을 식별하지 못했다. 이 표기는 CPU 사용률이나 정지 시간 자체가 아니다. Windows CPU 추적은 프로파일 정책 오류 `0xc5585011`로 시작하지 못했고 기록이 실행 중이 아님을 확인했다. 자동 승인 거절이 아니며 Windows 정책은 변경하지 않았다. 새 자료로 회귀 배수·전체 속도 해결·GC 제거를 주장하지 않는다. 도구 캡처·계측·백그라운드·캐시·초기 비교의 빌드 서버/메모리 영향은 남은 교란 요인이다.

로컬 `artifacts/a439-followup/normal-comparison.json`, `results/`의 `preskin-folder-detail-r1`·`current-folder-detail-r1`과 대응 actions, `current-idle-detail-r1`·`current-pointer-away-r1`, `current-*-profile.nettrace`에 근거를 보존했다. 준비 소스 해시·빌드·계측 manifest와 `ui-restoration.json`이 조건을 연결한다. 검수는 정상 종료했고 Test 원본 28키를 바이트 복원했다. 공식 43키는 시작 전과 같으며 공식 앱·Windows 설정을 조작하지 않았다.

### 메뉴 수정안의 정상 빌드와 화면 검증

시작 메뉴 항목에 네이티브 `SubtleButtonStyle`을 공유하고 기존 글꼴·시스템 초점 표시·크기·배치를 유지하는 수정안을 정상 publish했다. 이 스타일은 테마별 hover/pressed/disabled 자원을 사용하며 조회에 실패하면 진단을 남기고 기존 네이티브 버튼으로 돌아간다. 루트 소스 658파일과 native 참조 override 1개, 글꼴·라이선스 34개, 정상 진입점과 당시 진단 타입 부재를 대조했다. 로컬 native DLL은 기존 검증본을 재사용했다. 당시 DLL 식별자와 화면 근거는 `artifacts/a439-followup/menu-ui-verification.json`에 보존했다. 그 파일의 원래 `NormalBuild` 참조인 `product-build-verification.json`은 최신 빌드로 덮어쓰는 경로이므로 지금 내용을 첫 메뉴 빌드의 근거로 쓰지 않는다. 이 첫 검증은 `MainWindow.xaml.cs`만 수정한 상태이며 이후 캐시 수리와 최종 정상 검증은 아래 후속 절을 따른다.

계측 없는 정상 빌드의 라이트와 단계 복사본에서 `Application.RequestedTheme=Dark`를 초기화 전에 적용한 전체 앱 다크 시작에서 메뉴 강조와 키보드 초점을 관측했다. 후속 계측 시작 전 직접 메뉴 버튼 10개가 모두 실제 `SubtleButtonStyle`을 참조함을 확인했고 글꼴 14·아이콘 16·간격 12·최소/실제 높이 36·패딩 10,8·시스템 초점 표시를 기록했다. 메타데이터 수집 때 메뉴가 닫혀 `IsLoaded=false`·`ActualWidth=0`이므로 실제 폭 통과로 해석하지 않는다. 포인터 위치는 우클릭으로 옮겼으며 순수 호버 입력이 아니다. 자동화의 파란 커서 효과를 제품 그림자로 세지 않는다. 다크 시작은 OS 테마 변경이나 실행 중 전환 검증이 아니며 Windows 설정 실행은 도구 응답 오류로 실패했다. 화면·런타임 조건은 `menu-ui-verification.json`과 연결된 Light/Dark PNG·`MenuSetup` 결과를 따른다.

### 응답 대조와 네이티브 스택

단계 전용 `A439ResponsivenessProbe`는 우선순위별 대기 콜백을 하나로 제한해 High/Normal/Low 디스패처 대기와 별도 워커의 호출 지터를 기록한다. v1의 `DispatcherPings=false`도 100ms 워커는 남으므로 무워커 대조가 아니다. v2의 `SampleWorker=false`·`DispatcherPings=false`는 워커를 시작하지 않고 Rendering 콜백만 기록한다. 고정 버퍼·오버플로 기록, 측정 전 메뉴 메타데이터와 종료 후 저장을 사용하며 강제 GC·측정 중 트리 탐색은 없다. 콜백 간격과 큐 대기는 물리 입력부터 GPU 표시까지의 지연이 아니다.

빈 뷰의 다크·라이트 회차에서는 2초 이상 공백이 없었다. 같은 709×535 창·TXT 240개 `folder-a`에서는 다음을 관측했다. 전체 회차 조건과 값은 `artifacts/a439-followup/responsiveness-summary.json` 및 `results/response-*`에 둔다.

| 조건 | 구간 | 최장 Rendering 간격 | 2초 이상 간격 |
|---|---:|---:|---:|
| Preview, v2 무워커 | 49.007초 | 2,570.871ms | 12회 |
| Preview, 워커·세 우선순위 관측 | 66.072초 | 2,617.627ms | 16회 |
| List, v2 무워커 | 47.611초 | 427.687ms | 0회 |

Preview의 세 우선순위 관측 회차는 큐 대기 최대 약 2.58초·p95 약 2.4초였고 해당 구간의 프로세스 GC 정지는 0이었다. 이를 GC 전체 제거로 확대하지 않는다. List 회차에는 진단 helper 준비·빌드가 겹쳤으므로 엄밀한 동일 조건 대조가 아니며, Preview 타일 경로를 우선 조사할 근거로 한정한다. 외부 CPU 표본·관리 추적을 수집할 때 긴 공백이 줄어드는 관측 변화가 있었으나 인과는 미확정이다. 캡처 전후 대조도 캡처 자체를 원인으로 확정하지 못했다. 측정 중 컴퓨터 도구에 UIA 조회를 요청하지 않았다는 조건은 시스템 전체에 UIA 호출이 없었다는 보증이 아니다.

별도 시점의 네이티브 덤프 세 개를 Microsoft 공식 DbgEng와 심볼로 오프라인 분석했다. 모두 UI 스레드에서 WinUI `ItemsControlAutomationPeer::GetModernItemsControlChildrenChildrenHelper`·`ListViewBaseAutomationPeer::GetChildrenCore`, `ContainerFromItem` 또는 `GetItemPeerFromChildrenCache`와 UIAutomationCore `CrossProcess_BulkFetch`·`RemoteUiaNodeStub::Incoming_BulkFetch` 경로를 확인했다. 이는 구체적인 외부 UIA 요청 처리 경로의 관측이며 요청 클라이언트의 신원·발생 조건이나 전체 지연의 원인 입증은 아니다. 성능 회차 밖에서 수행한 덤프 수집 자체도 각각 약 1.21/0.92/0.92초가 걸렸으므로 그 간섭을 대기 시간에 합치지 않는다. 근거는 `results/native-preview-r1-stack.json`부터 `r3`까지와 각 `.dmp.capture.json`, 도구의 `tools/native-stack/abi-evidence.json`·`usage-and-validation.json`이다. WPR 정책을 우회하거나 Windows 설정을 바꾸지 않았다.

### 캐시 범위의 반전 검증과 후속 수리

빌드·프로파일러를 중단한 같은 프로세스에서 Preview→List→Preview를 비교했다. Preview의 긴 큐 대기가 재현됐고 List에서는 2초 이상 Rendering 공백이 없었지만, 마지막 Preview의 대부분 구간도 조용했다. 외부 요청 빈도가 일정하다는 보증은 없다. 조건·원자료는 기존 `responsiveness-summary.json`의 `MatchedModeComparison`과 대응 actions에서 회수한다.

사용 중인 WinUI DLL의 소스 커밋 `c03f50c96989525a1487cf9404f2306b314a23d0`를 대조했다. [항목 자식 열거](https://github.com/microsoft/microsoft-ui-xaml/blob/c03f50c96989525a1487cf9404f2306b314a23d0/dxaml/xcp/dxaml/lib/ItemsControlAutomationPeer_Partial.cpp#L278-L341)는 화면 밖을 포함한 캐시 구간 전체에서 피어·컨테이너를 찾으며, [다음 형제 탐색](https://github.com/microsoft/microsoft-ui-xaml/blob/c03f50c96989525a1487cf9404f2306b314a23d0/dxaml/xcp/dxaml/lib/AutomationPeer_Partial.cpp#L314-L337)은 부모 자식 목록을 다시 요청한다. 세 네이티브 스택과 같은 경로다. [CacheLength 계약](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.itemswrapgrid.cachelength?view=windows-app-sdk-1.8)의 기본값은 4이며 화면 밖 선행 생성량을 정한다.

단계 계측 v3는 측정 전 한 번만 제한된 트리 탐색으로 실제 캐시·표면을 읽고, 별도 F8 준비에서 캐시값을 바꾼다. F10 측정 중에는 탐색·캐시 변경을 하지 않는다. 실행 중 4→1 대입의 읽기 확인은 성공했지만 대기와 스크롤 왕복만으로는 기존 216개 컨테이너가 줄지 않았다. 이 회차들을 유효한 축소 비교로 세지 않는다. 부모 폴더 이동 후 같은 폴더에 재진입하자 캐시가 줄었고 다음 반전 결과를 얻었다.

| 동일 프로세스의 캐시값 순서 | 실제 캐시 항목 | High 큐 최대 대기 | 2초 이상 Rendering 공백 |
|---|---:|---:|---:|
| 1 | 90 | 520.808ms | 0회 |
| 4로 복원 | 216 | 2,501.697ms | 6회 |
| 다시 1 | 90 | 560.097ms | 0회 |

각 회차는 같은 709×535 창·TXT 240개와 부모 타일을 합한 241항목·가시 범위 0~47을 유지했다. 캐시 규모의 지연 기여는 줄이기·복원의 반복으로 확인했으며, 네이티브 UIA 반복 탐색이 그 비용 경로를 설명한다. 측정 구간은 44.701/34.781/42.432초로 다르고 GC 정지도 39.519/84.991/45.194ms였다. 외부 클라이언트 신원·요청 빈도, 전체 입력 지연이나 스킨 도입 회귀 배수까지 확정한 것은 아니다. 별도 접근성 스냅샷 API의 짧은 반환 시간은 새 네이티브 UIA 요청의 수행 시간으로 세지 않는다. 근거는 `CacheExperiments`, `results/response-cache*-reload-*`, `response-cache-actions.json`·`response-cache-snapshot-returns.json`이다.

수정안은 `TileGrid.ItemsPanel`에 기존과 같은 네이티브 `ItemsWrapGrid`·가로 방향을 명시해 생성 시점부터 캐시를 제한한다. 첫 `CacheLength=1` 제품 후보는 런타임 조작 없이 6열에서 90개 캐시·최대 High 큐 대기 516.804ms·2초 이상 공백 0회를 확인했다. 그러나 좁은 창의 12열에서는 180개 캐시·1,334.387ms가 남았다. 같은 12열에서 단계 준비로 0.25를 적용하고 폴더에 재진입하자 가시 96개와 전체 241항목을 유지한 채 캐시 108개·최대 대기 347.978ms로 줄었다. 큰 폭 휠 이동 후 타일 표시, 클릭 선택→End→Enter로 마지막 `item-240.txt` 열기와 내용 표시를 확인했다. API의 오래된 초점 설명은 실제 키보드 동작 근거로 세지 않았다.

이 첫 후보의 근거는 `results/response-product-cache*`, `response-product-cache-actions.json`과 `product-cache025-*.png`다. 단계 적용 결과와 뒤의 소스 자체 빌드·최초 생성 검증은 구분한다.

### 크기 변경 때의 과다 실현과 측정 전 치수 적용

캐시 0.25 소스 자체의 정상 publish와 v3 계측 빌드를 마친 뒤, 런타임 캐시 덮어쓰기나 F8 없이 작은 창 6→9→12열에서 2560×1032로 최대화했다. 캐시 속성은 0.25였지만 측정 전 스냅샷에서 가시 60개에 전체 241개 컨테이너가 남았다. 43.873초 회차에서 High 큐 최대 대기 3,034.558ms·2초 이상 Rendering 공백 13회를 관측해 캐시값만 바꾸는 후보의 한계를 확인했다. 회차 중 큰 휠 이동은 있었으나 전체 컨테이너 관측은 그 이전이다. 작은 창 최초 6열과 12열 결과를 포함한 실패 근거는 `results/response-final025-*-r1.json`과 `responsiveness-summary.json`의 `Final025Checks`에 보존한다.

정확한 WinUI 소스의 [컨테이너 생성 루프](https://github.com/microsoft/microsoft-ui-xaml/blob/c03f50c96989525a1487cf9404f2306b314a23d0/dxaml/xcp/dxaml/lib/ModernCollectionBasePanel_Partial.cpp#L1280-L1328)는 기존 컨테이너가 있으면 계속 진행하며 새 컨테이너에만 생성 범위 조건을 적용한다. [ItemWidth/Height 변경](https://github.com/microsoft/microsoft-ui-xaml/blob/c03f50c96989525a1487cf9404f2306b314a23d0/dxaml/xcp/dxaml/lib/ItemsWrapGrid_Partial.cpp#L110-L138)은 측정 무효화와 [캐시 버퍼 재설정](https://github.com/microsoft/microsoft-ui-xaml/blob/c03f50c96989525a1487cf9404f2306b314a23d0/dxaml/xcp/dxaml/lib/ModernCollectionBasePanel_WindowManagement_Partial.cpp#L771-L790)을 수행하지만 그 자리에서 기존 컨테이너를 제거하지 않는다. 이는 앞선 런타임 축소 시 컨테이너 유지 관측과 맞는다. 확대된 뷰포트를 이전 작은 타일 치수로 먼저 측정해 과다 실현한 뒤 치수를 보정한다는 원인 추론에 따라 적용 시점을 수정했다.

새 후보는 `ThumbnailExplorer.MeasureOverride`에서 들어온 가용 폭으로 기존 네이티브 패널의 치수를 먼저 적용한다. 첫 패널은 [네이티브 측정 전에 발생하는 Loading](https://github.com/microsoft/microsoft-ui-xaml/blob/c03f50c96989525a1487cf9404f2306b314a23d0/dxaml/xcp/core/core/elements/framework.cpp#L1474-L1498)에서 같은 폭을 사용한다. 열 변경도 측정을 무효화하고 실제 치수가 바뀔 때만 기존 논리 앵커 보호를 적용한다. 이전 뷰포트 폭으로 새 폭을 다시 제한하지 않으며 기존 배치 후 보정식은 유지한다. ItemsSource·패널·선택·접근성 피어를 교체하지 않고 고정 6/9/12열·타일 비례 계산을 보존한다.

`response-measure025-normal-build.json`은 정상 진입점·658개 제품 소스·34개 글꼴/라이선스 일치와 probe 부재를 확인했다. 로컬 native DLL 재사용은 공식 전체 native 빌드를 대체하지 않는다. 이어 새 계측 빌드 `response-measure025-r1`을 소스 캐시 0.25·F8/런타임 덮어쓰기 없이 검수했다.

| 치수 적용 수정 후 회차 | 실제 캐시 / 가시 항목 | High 큐 최대 대기 | 2초 이상 Rendering 공백 |
|---|---:|---:|---:|
| 작은 창 최초 6열 | 54 / 48 | 391.664ms | 0회 |
| 같은 6→9→12열→최대화 순서 | 108 / 60 | 408.951ms | 0회 |
| 새 프로세스 큰 창 최초 6열·혼합 파일 | 36 / 30 | 567.390ms | 0회 |

각 회차는 48.308/57.132/227.687초이며 마지막에는 컨텍스트 압축 대기가 포함됐다. 앞의 실패 회차와 수정 후 최대화 회차 모두 2600 휠 왕복을 사용했지만 기간·입력 시점이 같지 않은 단회 결과다. GC 정지도 각각 23.512/241.773/594.695ms로 남아 있다. 이 관측은 치수 적용 시점 수정 후 해당 과다 실현 재현이 줄었음을 뒷받침하며 모든 지연 해결·스킨 회귀 배수·GC 제거·물리 입력 지연을 증명하지 않는다. 원자료와 전체 수치는 `results/response-measure025-*-r1.json` 및 `responsiveness-summary.json`의 `ResizeSizingCandidate`에서 회수한다.

계측본에서 작은/큰 창 6·9·12열 배치, 큰 휠 이동, 열·창 크기 변경 후 `item-101` 선택 정보 유지, 타일을 다시 클릭한 뒤 End→Enter로 `item-240.txt` 본문 표시를 확인했다. 제목줄 조작 뒤 Enter는 전체 화면 전환으로 이어졌으므로 전체 키보드 초점 유지나 정확한 픽셀 앵커 통과로 세지 않는다. 새 프로세스의 큰 창 혼합 241항목은 PNG/TXT 내용과 PDF 확장자 대체 표시까지 관측했고 PDF 썸네일은 미확인이다. 근거는 `results/response-measure025-actions.json`과 `measure025-*.png`다.

새 치수 적용 코드·원자료 수치·문서의 독립 검토에서 구체적 결함을 찾지 못했다. 위 계측 결과와 다음 정상 제품 후보의 기능 검증은 구분한다.

### 정상 제품 후보의 최종 로컬 검증과 배포 준비

root 원본을 `normal-source`에 다시 복사해 메뉴·캐시·치수 적용 수리를 함께 정상 publish했다. `artifacts/a439-followup/final-normal-build.json`은 제품 소스 658개·글꼴/라이선스 34개 일치, 정상 `Program.Main`, Test=true·Standalone=false, 네 종류 A439 probe·진단 하네스 부재를 확인한다. 강제 테마도 없으며 `final-validation.json`의 전체 시험은 1,553개 통과·실패/건너뜀 0이다. 별도 Standalone 빌드는 경고/오류 0과 Test=false·Standalone=true를 확인했다. 이 로컬 검증의 제품 버전은 v0.436.0이며 native DLL은 기존 검증본을 재사용했다.

이 무계측 정상 앱의 709×535 라이트 화면에서 메뉴 항목 강조와 Tab 키의 네이티브 초점 표시를 확인했다. Archive 우클릭으로 포인터를 옮겼으므로 순수 호버 입력은 아니며 파란 커서 효과는 제품 표시에서 제외한다. TXT 240개와 부모 타일의 작은 6→9→12열 후 2560×1032 최대화, 2600 휠 아래/위 왕복을 확인했다. 이어 `item-029`를 클릭하고 큰 9→6열로 바꿨을 때 선택 정보가 유지됐으며 추가 타일 클릭 없이 End로 `item-240` 선택 후 Enter로 TXT 본문을 열었다. 이는 해당 열 변경 키보드 경로의 기능 확인이며 제목줄 조작 후 초점·전체 초점 유지·정확한 픽셀 앵커나 새 지연 측정으로 확대하지 않는다. 앞선 혼합 파일의 PDF 확장자 대체 표시도 PDF 썸네일 통과로 바꾸지 않는다.

근거는 `final-normal-ui.json`·`final-normal-*.png` 13개다. 앞선 메뉴 단독/강제 다크 단계와 현재 정상 UI의 DLL·화면 근거는 서로 구분한다. 검수 앱을 Alt+F4로 정상 종료한 뒤 프로세스 없음과 Test 원본 28키 바이트 복원, 공식 43키·OS 불변을 `ui-restoration.json`에 기록했다.

이후 v0.437.0과 변경 설명을 반영한 정상 publish에서도 제품 소스·34개 글꼴/라이선스·정상 진입점·배포 식별자와 진단 타입 부재를 대조했다. 근거는 `versioned-normal-build.json`이며 필수 검사와 최종 독립 검토도 통과했다. 제품 커밋과 즉시 push, 공식 전체 native CI·자산/피드/해시 및 이 PC 공식 Updates 설치·재시작·파일/설정/로그 대조가 남았다. 공식 제품과 설치본은 아직 v0.436.0이다. 별도 보호 백업 `artifacts/a439-followup/pre-update-backup/`과 상위 기준 JSON은 재생성·덮기 없이 설치 직전에 재검증한다. 현재 배포 단계는 [HANDOVER](../../HANDOVER.md), 미관측 환경과 기존 충돌 조사는 각 정본을 따른다.

### 도입 전후 코드 조사

도입 전 `f74a289`와 도입 `db101e7` 이후를 대조했다. 네이티브 컨트롤 상태 표현을 전역 사용자 정의 템플릿과 [LiveDesign](../../../src/KOTU.App/Appearance/LiveDesign.cs)의 요소별 상태 관리로 바꾼 것이 주요 구조 변화다. 단순 래퍼 한 겹의 추가로 설명하지 않는다.

- 호버·초점·선택·눌림과 일부 네이티브 상태 변경이 즉시 `Refresh`/`Apply`로 모인다. 동일한 최종 상태를 생략하는 캐시가 없어 한 조작의 여러 경로가 겹칠 수 있다.
- [DesignSurface](../../../src/KOTU.App/Appearance/DesignSurface.cs)는 그릴 때 자식을 비우고 도형·브러시를 다시 만들며, [DesignOverlay](../../../src/KOTU.App/Appearance/DesignOverlay.cs)는 즉시 그린 뒤 Arrange를 무효화한다. Original도 이 경로를 사용한다.
- 최초 `Track`의 `Load` 내부 갱신과 외부 `Refresh`가 중복된다. 팝업·가상화 컨테이너의 여러 연결 요청, 원본과 오버레이 양쪽의 크기 변경 처리도 겹칠 수 있다.

위 경로는 코드로 확인한 추가 작업이다. 매 프레임 전체 트리를 무한 순회하거나 동일 핸들러가 무제한 누적되는 결함, 일반 호버 경로의 동기 파일 I/O는 이번 정독에서 확인하지 못했다. 과거 A427 하네스의 GC 지연 자료는 비교군 작업량·관측 횟수·측정기 할당 영향이 달라 현재 지연의 배수나 원인 증명으로 쓰지 않는다. 현재 Original과 단일 활성 스타일의 동일 조작 비교로 기여도를 판단한다.

근거는 로컬 `artifacts/a439-review/results/`의 `baseline-menu-r2`, `baseline-folder-r2`, `baseline-resize-r1`과 `candidate-menu-r1`, `candidate-folder-r1`, `candidate-resize-r1` 결과 JSON·대응 `-actions.json`이다. 입력 뒤 화면만 캡처했으며 측정 도중 UIA 전체 트리·강제 GC·결과 파일 쓰기는 하지 않았다. 우클릭을 포함하므로 순수 호버 실험으로 부르지 않는다. UI 할당은 계측 영향을, GC는 다른 스레드의 작업도 포함한다. 디스패처 대기 시간은 입력부터 렌더까지의 지연이 아니며 inclusive AttachTree/Load/Refresh 시간과 중첩 Draw 호출은 합산하지 않는다.

기존 첫 폴더 회차 `baseline-folder-r1` 후 캐시를 지우지 않고 새 프로세스에서 반복해도 큰 비용이 유지됐다. 후보도 캐시를 지우지 않았다. 요청 간격 차이, 후보 트리에 일시적으로 남은 시험 결과 폴더 한 항목, 스냅샷과 프로세스 전체 GC 영향 때문에 엄밀한 마이크로벤치로 보지 않는다. 후보 세 회차의 AttachTree/Load/Refresh·도형 그리기 호출은 모두 0이며 추가 스킨 처리와 관리 할당·GC 정지 감소가 확인됐다. 반면 폴더의 최장 디스패처 대기는 2,638.83→2,711.12ms로 줄지 않았고 메뉴 p95도 289.44→295.51ms로 비슷했다. 전체 입력 지연 해결이나 개선 배수로 확대하지 않는다.

첫 `baseline-menu-r1`은 WinUI 네이티브 오류로 종료돼 결과가 없으며 비교에서 제외한다. 같은 DLL의 유휴 명시 정지·10초 자동 종료, 메뉴를 열어 둔 15초 자동 종료와 변경 전 네 회차·후보 세 회차는 저장 후 프로세스 생존을 확인했다. 따라서 자동 종료가 원인이라는 추측은 채택하지 않으며 최초 충돌 원인은 미확정이다. WER와 실패 조작 기록을 보존한다. 종료 뒤 검수 설정은 원본 바이트로 복원했고 공식 앱은 조작하지 않았다.

### 메뉴 호버 누락의 코드 근거

시작 메뉴의 모듈 항목은 일반 Button이다. 변경 전 v0.435.0의 전역 `KotuButtonTemplate`은 `PointerOver` 상태를 비우고 [CommandColors](../../../src/KOTU.App/Appearance/LiveDesign.Appearance.cs)에 표시를 맡겼다. 이 자원은 후보의 [비활성 자원](../../../src/KOTU.App/Appearance/MultiDesignResources.xaml)에 보존했다. [OriginalDesignPalette](../../../src/KOTU.App/Appearance/OriginalDesignPalette.cs)가 평상시와 호버에 사용하는 `ControlFillColorDefault`와 `SubtleFillColorSecondary`는 현재 WinUI 다크 리소스에서 모두 `#0FFFFFFF`이며 같은 배경에 합성된다. 폴백도 같은 색이다. Original 도형에 별도 호버 변화가 없어 다크에서 시각 변화가 사라지는 경로다. 라이트의 두 토큰은 달라 같은 증상으로 확대하지 않는다. 실제 원래 디자인과 복원 결과는 화면으로 대조한다.

### 복원 후보 구현

기존 스킨 구현·카탈로그·자료와 저장된 `display.design`은 보존하되 선택 UI와 동적 스킨 런타임은 활성 제품 경로에서 사용하지 않는다. `AttachWindow`만 끄지 않고 Managed/직접 등록·구독도 상태 생성 전에 차단한다. 빈 상태 템플릿과 투명 자원을 그대로 두면 체크·선택·호버가 사라지므로, 단일 활성 스타일에 네이티브 상태와 원래 테마를 함께 복원한다. 버튼·바·트리 공통 치수, A426 배치와 A433 고정 열/비례 조작부, 원래 독립 설정인 `display.thinControls`는 유지한다. 메뉴의 normal/hover/pressed/disabled/키보드 focus를 다크·라이트·고대비에서 확인하고 열린 모듈·문서·선택 상태는 재생성하지 않는다.

후보는 `DesignRuntime.MultiSkinEnabled` 정책으로 활성 프로필과 저장 선택을 분리한다. `LiveDesign`의 모든 등록 진입점과 `DesignScope.RequestManagement`를 차단하고, 공통 아이콘은 고정 글리프를 사용한다. 다만 `DesignScope.SetRole`·`SetOriginalFontSize`의 약한 참조 상태 저장은 남아 있으므로 모든 상태 생성이 없어졌다고 확대하지 않는다. 기존 App 자원 57개와 커스텀 템플릿은 [비활성 자원](../../../src/KOTU.App/Appearance/MultiDesignResources.xaml)에 보존했다. 활성 [App.xaml](../../../src/KOTU.App/App.xaml)은 네이티브 상태와 기존 조작부 치수를 사용하며, 열린 파일의 굵기는 엔진 없이 직접 반영한다. 구현 자료 보존은 스위치 한 줄로 전체 기능을 재활성화할 수 있다는 약속이 아니다.

후보의 Core 시험 778개와 독립 코드 검토를 통과했다. 라이트에서 6열 타일의 비례 체크 표시·선택 분리, TXT 열기, 비활성 Fit 메뉴와 저장된 `ink`의 보존·스킨 선택 UI 숨김을 확인했다. 루트 `RequestedTheme`만 다크로 바꾼 최초 진단에서는 하드웨어 패널이 라이트로 남았으나, 다음 단계 복사본에서 `Application.RequestedTheme`을 초기화 전에 다크로 설정하자 해당 배경도 다크로 표시됐다. 이 전체 앱 다크 시작에서 메뉴 호버·키보드 초점, 체크·현재 선택 분리와 TXT·비활성 Fit 항목을 관측했다. 루트만 바꾼 혼합 화면은 진단 범위의 차이이며 실제 OS 테마 변경·실행 중 전환 성공을 증명하지 않는다. Windows 설정 실행은 같은 도구 응답 오류로 실패했고 OS는 변경하지 않았다.

v0.436.0의 계측 없는 전체 publish·1,553시험과 진단 타입 부재·34글꼴/라이선스 대조를 통과했다. 이 정상 검수본의 라이트 시작·Display에서 스킨 선택 UI 숨김과 저장된 `ink` 보존도 확인했다. 로컬 native DLL은 기존 검증본을 재사용했고, 이후 공식 CI의 전체 native 빌드·시험·설치·Standalone 검증과 v0.436.0 공식 배포·이 PC 설치를 완료했다.

화면과 빌드 조건은 로컬 `artifacts/a439-review/`의 `candidate-light-*`·`candidate-root-dark-menu-*`·`candidate-app-dark-*`·`candidate-display-settings.png`·`product-light-*`와 준비 manifest, `product-build-verification.json`·`test-results/`·`ui-restoration.json`에서 회수한다. 두 계측 파일과 강제 다크 설정은 단계 복사본에만 적용했으며 제품에는 포함하지 않는다. 현재 검수 경계는 [실기기 확인](../../DEVICE-CHECKS.md#a439), 배포·설치는 [현재 상태](../../HANDOVER.md)를 따른다.

## 오프라인 글꼴

시스템 글꼴은 이름으로 참조하고 복사하지 않는다. Nunito Sans와 Barlow Semi Condensed의 한글은 Malgun Gothic으로 보완한다. 편집물의 한글 제목에는 선택 설치인 Batang 대신 Nanum Myeongjo를 동봉한다. 터미널·픽셀·손그림은 한영을 같은 가족으로 표시한다.

동봉 대상은 Nunito Sans Regular/SemiBold, Barlow Semi Condensed Regular/SemiBold, Nanum Myeongjo Regular/Bold, Nanum Gothic Coding Regular/Bold, Galmuri11 Regular/Bold, Gaegu Regular/Bold다. 원본을 수정하지 않고 각 가족의 SIL OFL 1.1 저작권·라이선스 전문과 함께 배포한다. 다운로드 후 TTF 내부 family 이름·문자 지원·크기·해시를 기계적으로 확인한다.

원본 검증에서 두 Nanum 가족과 Galmuri11은 각 두께 모두 한글 음절 11,172자와 인쇄 가능한 ASCII 95자를 포함했다. Gaegu는 한글 2,350자만 포함하고 백틱이 없어 드문 한글·누락 기호에 시스템 보완 글꼴이 필요하다. WinUI 파일 참조의 가족 이름은 `NanumMyeongjo`, `NanumGothicCoding`처럼 공백이 없다. 검증 원본·라이선스·출처와 해시는 로컬 `artifacts/a427-review/fonts/manifest.json`에 있다. 실제 네이티브 렌더링 확인은 별도 단계다.

- [Nunito Sans 원본](https://github.com/googlefonts/NunitoSans/tree/058bd7a2f33d6ad5ef1df985b3db403622016a8c/fonts/ttf)과 같은 커밋의 `OFL.txt`.
- [Google Fonts 고정 원본](https://github.com/google/fonts/tree/06bfe0d62a98375cb09c942fa18e68bd32cff057/ofl)의 `barlowsemicondensed`, `nanummyeongjo`, `nanumgothiccoding`, `gaegu` 폴더와 각 `OFL.txt`.
- [Galmuri 고정 원본](https://github.com/quiple/galmuri/tree/bdb86ae89466a361eb8df861222736b81ff975ef/dist)의 `Galmuri11.ttf`, `Galmuri11-Bold.ttf`, `LICENSE.txt`.

## 설정에서 선택

- 2026-11-23 [A428](../../REQUIREMENTS.md#a428) 요청으로 선택 화면은 **갤러리 하나**로 제공한다. Single view, 보기 전환 라디오, 이전/다음, 별도 큰 미리보기, Show applied design, Open single view와 별도 적용 버튼은 제거한다.
- 갤러리는 전체 화면 썸네일 12개를 적응형 열로 나란히 보여 준다. Original이 첫 항목이다. 높이가 부족하면 설정 화면을 스크롤한다. 카드를 선택하면 그 디자인을 즉시 적용하며 선택 대기·미리보기 상태를 따로 두지 않는다.
- 현재 적용된 카드에만 **Applied** 표식과 강조 테두리를 표시한다. 다른 설정 창에서 바꿔도 같은 표식으로 갱신한다.
- 카드의 작은 예시는 같은 파일·한영 이름·체크·현재 선택·비활성 상태를 사용한다. 실제 사용자 파일이나 모듈을 열지 않으며 실제 UI와 같은 디자인 정의를 사용한다.
- A434부터 기본값은 Original이다. 안정적인 문자열 ID를 `display.design`에 저장하고 키가 없거나 알 수 없는 ID는 기본값으로 처리한다. 기존 11종의 명시적 ID는 유지한다. 기존 `display.thinControls` 키를 삭제하거나 덮어쓰지 않으며 Original에서만 이전의 얇은 조작부 선택을 해석한다.

제거 기능의 복원 기준은 [v0.433.0 제품 커밋](https://github.com/zpstudios/kotu/commit/db101e765d12a35a77f954d2674b18bb912221cc)이다. 당시 `DesignPicker.cs`, `DesignSelection.cs`와 관련 테스트·가이드가 Git에 보존된다. 복원 시 그 구현과 A428 변경을 비교해 필요한 부분을 되살리고 검증한다. A428 당시에는 Single view·이전/다음 등 갤러리 외 제거 기능의 숨은 옵션·사용하지 않는 구현이나 별도 소스 사본을 남기지 않는 정책이었다. 이 정책을 A439에서 비활성화할 스킨 구현·자료에 적용하지 않는다. 해당 자료에는 2026-11-26 사용자의 구현 보존 지시가 우선한다.

## 적용과 보존

- 열린 창과 나중에 생성되는 창·메뉴·가상화된 목록 요소에 같은 선택을 적용한다. Standalone도 현재 세션 안에서 선택할 수 있다.
- 적용 때문에 창이나 모듈을 다시 만들거나 파일을 다시 열지 않는다. 미저장 문서·재생·체크/선택·스크롤·패널 상태를 보존한다.
- 글꼴·아이콘과 버튼·체크박스·기호·입력·정보 표·패널 경계·하단 면을 함께 다룬다. 문서 원문·코드·자막 등 콘텐츠 자체의 글꼴은 기존 역할을 유지한다.
- 명암 테마는 디자인과 별개이며 시스템 Light/Dark를 따른다. 고대비에서는 시스템 상태색과 포커스 식별성을 우선한다. 외부 글꼴은 라이선스와 함께 동봉하고 실행 중 CDN을 사용하지 않는다.
- 하단 높이 44, 기본 버튼 32×32, 텍스트 조작부 84×32와 A426의 공통 버튼 위치를 유지한다. A112 Back/Esc와 F11/F12의 패널 동작도 유지한다.
- 체크한 작업 대상·현재 선택·열린 콘텐츠 표시는 서로 다른 의미로 남긴다. hover/pressed/disabled/focus/mixed 상태를 확인한다.

### 실제 요소 연결 원칙

- 아이콘의 의미와 디자인 정의를 명시 입력으로 받는 같은 팩토리를 실제 UI와 미리보기에서 사용한다. 모듈마다 연결된 Shared 코드의 정적 상태를 공유 상태로 가정하지 않고 Core의 디자인 선택을 단일 출처로 삼는다. 미리보기와 팩토리 내부 도형은 전체 UI 갱신의 하위 탐색에서 제외한다.
- 현재 창의 실현된 요소와 새 창·가상화 컨테이너·팝업은 Loaded 때 연결하고 Unloaded·Closed에서 구독을 정리한다. 갱신은 UI 디스패처에서 수행하며 매 프레임 전체 시각 트리를 훑거나 데이터 항목을 전부 열거하지 않는다. 창을 닫을 때 분리된 요소도 정리할 수 있게 소유 루트를 기억한다.
- 실제로 로드된 요소에 뒤늦은 Unloaded가 오더라도 정상 정리를 먼저 수행한다. 같은 활성 창에 남은 요소에 한해 한 번 재연결을 예약하고, 실행 직전 세대·로드 상태·등록 루트·콘텐츠 제외 여부를 다시 확인한다. 창 종료나 루트 해제에서는 재연결하지 않는다.
- 이름 있는 FontIcon과 바인딩 대상은 같은 객체를 유지한다. 터미널 문자로 바꿀 때 원래 의미 글리프를 별도로 보관하고 외부 글리프 갱신·컨테이너 재활용을 반영한다. FontIcon 내부 글자의 서식은 소유 아이콘에 맡겨 문자 디자인에서 돌아올 때 이전 글꼴이 남지 않게 한다. 버튼 템플릿이 필요하면 초기 구성에만 설정하며 디자인 전환 때문에 모듈·콘텐츠를 옮겨 붙이지 않는다.
- 숨겨 만든 경로 표시줄의 아이콘, 일반 목록의 폴더·파일 아이콘, 새 Hardware 그래프·사양과 파일 메타 정보 글자는 생성 시점에 기존 디자인 수명 관리에 등록한다. Record 소스 템플릿은 같은 관리 setter를 가진 명시적 스타일을 사용한다. 실제 적용은 원래의 Loaded·등록 창·콘텐츠 제외 검증을 따르며, 진단 이벤트 구독에 기대어 제품 연결을 보완하지 않는다. 생성 등록을 위해 센서 갱신 주기나 사양 재생성 구조를 바꾸지 않는다.
- 체크·드롭다운·트리·슬라이더의 네이티브 입력·상태·포커스는 유지한다. 원래 템플릿 상태 대상을 제거하지 않고 필요한 표시 부분만 디자인 기호와 연결한다. 시스템 고대비에서는 재정의한 네이티브 상태 자원에도 시스템 색을 제공한다. 갤러리의 적용 카드 표식과 강조 외곽은 전체 디자인 갱신에서도 보존한다.
- 콘텐츠 제외 정보는 기존 의미 Tag를 덮어쓰지 않는 약한 역할 정보로 전달한다. 문서 편집·Markdown·가상 편집기·WebView·PDF·Office 페이지/본문·인쇄와 문서 텍스트 썸네일을 보호한다. 파일명·메타 정보·문서 도구막대는 UI로 남긴다. 녹음 상태의 빨간 표시와 그래프 의미색은 중립 팔레트로 덮지 않는다.
- 장식은 원래 요소의 외곽을 따르며 목록·패널의 원하는 크기를 늘리지 않는다. 여백이 있는 카드도 바깥 Border를 기준으로 그리고, 콘텐츠·입력 영역을 옮기지 않는다. 스크롤 손잡이·얇은 진행 채움·대기 회전은 네이티브 입력과 애니메이션을 유지하며 디자인 색·모서리·주변 조형을 적용한다.
- [A429](../../REQUIREMENTS.md#a429): 메뉴의 항목 사이·구분선·내부 여백은 연속된 배경으로 뒤 콘텐츠를 가린다. 컨트롤 배경 장식은 그 컨트롤의 직접 템플릿 루트에만 붙이며, 콘텐츠 안의 다른 버튼이나 부모 컨테이너를 대신 사용하지 않는다. 지원하는 장식 루트가 없는 기본·개별 스타일은 원래 배경을 유지한다.
- 크기·굵기는 직접 지정·스타일·네이티브 기본값과 부모 상속을 각각 구분해 한 번만 보정한다. 열린 파일 이름의 강조는 디자인의 기본 굵기 위에서도 구별하며, 새 창·늦게 만든 메뉴·재활용 항목에 누적 보정하지 않는다. 앨범아트의 검정 띠 위 흰 글자처럼 배경과 짝을 이룬 지역 대비색은 보존한다.

## A434 원래 기본 디자인 복원

2026-11-25 사용자는 스킨 추가 전에 쓰던 외형을 현재 공통 간격·획 규격에 맞춰 복원하고 첫 번째 기본 디자인으로 두도록 요청했다. 원형 기준은 `f74a289`와 당시 실제 화면 `artifacts/a431-review/preskin-selected.jpg`다. Precision은 별도의 디자인으로 유지한다. 과거 코드를 그대로 되돌리거나 원형의 미리보기 배치를 현재 탐색기에 이식하지 않는다.

Original은 중립적인 연속 면과 평평한 패널, KOTU Fit 조작부와 원형 기하 아이콘을 사용한다. 파일명·트리·입력 등은 원래 역할에 맞는 Segoe UI를 사용하고 현재 크기·강조 보정을 유지한다. 원형 아이콘의 중심선을 현재 공통 생성 경로에 연결해 벡터·FontIcon·미리보기의 윤곽을 맞춘다. `display.thinControls=true`이면 같은 `original` ID 안에서 Segoe UI Semilight 조작부와 얇은 아이콘을 사용한다. 별도 13번째 선택지를 만들지 않는다.

디자인 설정이 없는 스킨 도입 전 설정은 저장 내용을 변경하지 않고 Original로 해석한다. 명시적으로 선택할 때만 `display.design`을 저장하며 기존 11종의 문자열 ID와 선택, 무관한 설정을 보존한다. 새 기본값·알 수 없는 ID·기존 일반/얇은 설정의 직접 업그레이드와 선택 저장 후 재시작을 구분해 검증한다. 32-DIP 버튼·44-DIP 하단·22-DIP 트리, 현재 배치와 A433의 고정 6/9/12열·체크/상태 표시 비례 축소를 유지한다. 열린 콘텐츠와 선택·체크·입력 상태를 재생성하지 않는다. 실제 관측과 남은 조건은 [실기기 기록](../../DEVICE-CHECKS.md#native-media)과 [현재 상태](../../HANDOVER.md)에 기록한다.

## A431 미리보기와 실제 화면 차이 진단

2026-11-23 사용자는 Folded paper 실제 탐색기와 Applied 카드 화면을 첨부하고 진단·원인 파악까지만 요청했다. 제품 코드는 변경하지 않았다. 두 원본과 해시·좌표별 색상은 `artifacts/a431-review/actual-paper.png`, `preview-paper.png`, `reference-measurements.json`에 보존했다. 읽기 전용 확인 당시 공식 v0.433.3 제품 커밋 `cb30bb8`, 저장 디자인 `paper`, UI 배율 200%였으며 이는 첨부 촬영 시점을 확정하는 근거는 아니다.

근본 원인은 **디자인 정의를 공유해도 화면을 조립하는 규칙은 두 벌**이라는 점이다. [DesignPreviewRoot](../../../src/KOTU.App/Appearance/DesignPreviewRoot.cs)는 실제 앱 컨트롤을 넣지 않고 [DesignPreviewRenderer](../../../src/KOTU.App/Appearance/DesignPreviewRenderer.cs)의 900×482 고정 예시를 Viewbox로 축소한다. 실제 앱은 기존 컨트롤·레이아웃을 보존하면서 LiveDesign으로 외형을 바꾼다. 같은 DesignCatalog·DesignSurface·아이콘 도형을 사용한다는 사실만으로 전체 결과가 같아지지 않는다.

| 항목 | 코드로 확정한 차이 |
|---|---|
| 좌우 패널 | Paper 미리보기는 Card(`#FFFDF6`)와 바깥 여백 8 DIP를 사용한다. 실제 패널은 Panel(`#E1D9C9`)을 사용하며 기존 도크 경계를 따른다. 첨부에서도 밝은 종이 패널과 더 어두운 전체 높이 패널로 구분된다. |

기존 아이콘 시험은 공통 도형, 디자인 검수기는 팔레트 갱신·미리보기 격리·기존 치수 보존 등을 검사한다. 미리보기 전체와 실제 탐색기의 화면 동등성을 검사한 것으로 볼 수 없으며, 이전 11종 관측도 이 대조의 통과 근거로 확대하지 않는다. 이번 결론은 첨부 색상 측정·코드 대조·독립 검토에 근거하고 새 실화면 조작은 없었다.

### 사용성을 보존한 대표 검수

진단 후 사용자는 기존에 촘촘하게 조정한 트리 줄 간격 등 사용성을 유지할 필요와, 미리보기의 미감이 여백에 의존할 가능성을 함께 제기했다. 11종을 일괄 재설계하기 전에 Folded paper 한 종류의 실제 검수본으로 평가하는 제안에 “그렇게 해보자”라고 동의했다.

첫 구현은 이를 현재 Paper의 세 색상 적용만 조정하는 시험으로 잘못 좁혔다. 두 캡처는 모두 개편 후 같은 아이콘·접힌 모서리·트리 밀도·배치를 사용하므로 색상 보정 전후만 보여 준다. 2026-11-23 사용자는 이 비교로 원래 질문에 답할 수 없다고 지적했다. 해당 시험의 실제 관측은 [실기기 기록](../../DEVICE-CHECKS.md#native-media)에 보존하되 스킨 비교 완료 판정을 취소한다.

유효한 기준 화면은 사용자가 명시한 다음 두 가지를 구분한다.

| 기준 | 판단할 수 있는 것 |
|---|---|
| 같은 Folded paper를 원안의 여백·줄 간격·비율로 적용한 화면 | 기존의 촘촘한 트리와 주요 조작부 크기를 보존한 안에서 미감·정보량·조작성이 어떻게 달라지는가 |
| 스킨 개편 전 UI | 아이콘·컨트롤·패널·타이포그래피를 포함해 스킨 개편으로 무엇이 달라졌는가 |

이번 미감과 밀도의 상충을 판단하는 직접 비교는 첫 번째이며, 두 번째는 개편 자체의 변화 기준이다. 스킨 도입 커밋은 `db101e7`(v0.433.0), 그 직전 소스 기준은 `f74a289`(v0.432.2)다. 현재 스킨에서 색만 되돌린 화면을 개편 전 UI로 부르지 않는다. 원안 배치의 실제 실행 버전이 없는 경우 새 검수용 구현과 정적 미리보기를 구분하며, 갤러리 예시를 실제 앱 화면으로 표시하지 않는다.

밀도를 보존한 적용안은 색뿐 아니라 Paper의 아이콘 조형·접힌 모서리·층·선·글꼴을 원안과 대조한다. 같은 창 크기·배율·폴더 목록·선택 상태로 트리 22-DIP 기준과 버튼 32×32·하단 44 DIP의 유지 여부, 화면당 폴더 수·긴 이름·체크/선택/포커스·입력 동작을 평가한다. 기존과 동일한 항목도 명시하며, 검증 없이 아이콘 모양 등이 새로 바뀌었다고 주장하지 않는다. 기존 브랜드 제목줄 결정은 유지한다.

대표 비교 단계의 범위는 공식 설치와 분리된 로컬 검수본이었다. 당시에는 제품 코드·나머지 10종이나 공식 배포를 바꾸지 않고 결과를 본 뒤 사용자가 진행 범위를 정하기로 했다.

2026-11-23 정정 후 실제 개편 전 소스 검수본, 같은 Paper의 원안 수치 재현본과 밀도 보존안을 실행해 비교했다. 재현본은 실제 탐색기에 원안의 행 32 DIP·이름 13 DIP·패널 바깥 여백 8 DIP·타일 3열/153:106 비율/14·10 DIP 간격을 적용한다. 실제 중앙 폭에 맞춰 타일을 확대하므로 절대 153×106 크기는 아니며, 기존 25:50:25 도크·경로줄·상위 폴더 타일·파일 미리보기를 유지한다. 폴더 아이콘 크기 38 DIP만 원안 수치로 맞추며 두 Paper 안의 글리프 계열 자체는 같다. 이를 당시 존재했던 원안 실행 버전이나 갤러리 전체 복제로 부르지 않는다. 상세 계약은 `artifacts/a431-review/layout-trial-contract.json`, 실제 관측과 복원은 [실기기 기록](../../DEVICE-CHECKS.md#native-media)에 둔다.

대표 비교의 판단은 **기존 밀도에서도 Paper의 아이콘·접힌 모서리·층·글꼴은 유지되지만 넓은 여백이 주는 인상까지 같지는 않다**는 것이다. 여유 배치는 긴 타일 이름에 유리하고 한 화면의 정보량은 줄어든다. 비교 완료 당시 제품 소스는 바꾸지 않았고 별도 검수 앱의 설정 복원·정상 종료까지 마쳤다.

2026-11-24 사용자는 기존 밀도를 유지하고 배치 대신 모양을 바꾸는 진행을 승인했다. 선택한 Folded paper의 밀도 보존안을 제품 반영의 기준으로 삼는다. 트리 22 DIP, 기존 버튼 크기·타일 배치와 패널 비율을 유지하고 Paper의 종이 면·테두리·접힌 모서리·아이콘·글꼴을 대조한다. 이미 제품에 있는 Paper 도형을 새로 만든 것으로 보고하지 않는다. 검수 환경변수나 원안 재현용 행 간격·타일 비율 패치는 제품에 포함하지 않는다. A431은 Paper에 한정하며, 이후 승인된 나머지 10종은 아래 A432에서 진행한다.

v0.433.4는 일반 대비의 Paper에서 실제 좌우 패널을 Card색, 일반 파일 타일의 기본 면을 Background색으로 연결한다. 선택·호버 등 상태색은 그 다음에 계산한다. 명시 색이 없는 폴더 아이콘에는 해당 Light/Dark 팔레트의 Foreground를, 소유 항목이 비활성이면 Muted를 적용한다. 외부에서 지정한 색·바인딩을 보존하고 디자인·고대비·소유 항목 변경과 Unload에서 소유한 색과 콜백을 해제한다. 기존 Paper 도형·글꼴과 배치는 그대로다. 실제 화면 확인과 코드 검토의 경계는 [실기기 기록](../../DEVICE-CHECKS.md#native-media)을 따르며, 배포·설치는 [공식 절차](../../development/official-release-and-install.md)로 진행한다.

## A435 테마 전환과 필터 아이콘 색

v0.433.9는 탐색기 경로줄의 필터 아이콘이 최초 기본 브러시를 캐시하지 않는다. 필터가 없으면 기존 암시적 아이콘 스타일과 부모 버튼의 전경색을 상속하고, 활성 필터는 관리 아이콘 스타일을 기반으로 한 `ThemeResource AccentTextFillColorPrimaryBrush`로 표시한다. 필터 해제 시 활성 스타일의 로컬값을 지워 현재 테마·버튼 상태의 기본색으로 돌아간다. 필터 목록·선택 상태·도구 설명·배치·디자인별 기호와 글꼴은 유지한다. 실제 전환 관측과 한계는 [실기기 기록](../../DEVICE-CHECKS.md#native-media)을 따른다.

<a id="a432"></a>
## A432 나머지 디자인의 밀도 보존 외형 개선

2026-11-24 A431 공식 설치 확인 후 사용자가 나머지 10종에도 같은 방향의 진행을 승인했다. Precision line, Rounded humanist, Solid pictograms, Editorial typography, Terminal console, Mechanical controls, Bold frames, Dimensional tiles, Pixel grid, Hand-drawn ink를 미리보기와 대조한다. 색뿐 아니라 면·경계선·모서리·층·아이콘·타이포그래피의 실제 적용 차이를 확인하고, 이미 공유하는 조형은 새 변경으로 보고하지 않는다.

트리 22 DIP·기존 들여쓰기, 버튼 32 DIP·하단 44 DIP, 현재 타일 크기/열 수/간격·보기 모드, 패널 25:50:25와 기존 브랜드 제목줄을 유지한다. 미리보기의 넓은 여백·3열 비율이나 Editorial/Terminal의 예시 목록 배치를 실제 탐색기에 강제하지 않는다. 사용자 파일·콘텐츠 글꼴, 선택·체크·포커스·스크롤과 입력 경로도 보존한다. Paper의 면 매핑을 다른 디자인에 일괄 복사하지 않고 각 미리보기의 역할과 상태를 기준으로 결정한다.

디자인별 차이 분석 후 구현하며, 선택/체크·호버/눌림·비활성·Light/Dark·고대비·디자인 왕복과 새로 실현된 항목을 영향에 맞게 검증한다. 실제 관측과 코드 검토를 구분하고, 로컬 검수·버전/변경 설명·커밋/즉시 push·공식 배포·이 PC 공식 설치 대조까지 마친다. 공식 앱의 열린 사용자 작업은 기존 사전 확인·백업 절차로 보호한다.

v0.433.5는 일반 대비에서 정확한 탐색기 파일 타일 루트와 현재 소유 항목을 식별해 상태 장식을 한 계층에서 그린다. 일반 항목은 Frame의 상시 프레임, Editorial/Terminal의 구분선만 남기고 다른 7종의 면·외곽 장식은 제거한다. 체크 항목은 Panel, 선택 항목은 Selection 면을 쓰며 Solid 선택은 Accent 면과 OnAccent 파일명·폴더 기호를 짝지운다. 기존 내부 확장자 카드·미디어/문서 썸네일·명시 대비색·선택 외곽선·잘라내기 투명도는 각각의 기존 경로를 유지한다.

Editorial/Terminal 명령 버튼의 기본색은 Background/Foreground, 선택색은 Selection/Accent다. 입력 상자·메뉴·갤러리 Applied 표식은 별도 정책을 유지한다. 체크박스는 실제 20-DIP 표시 크기를 유지하면서 미리보기의 체크 전용 선 정책을 적용하며 라디오·혼합·비활성·고대비 상태의 의미는 바꾸지 않는다. 폴더색은 명시 값·바인딩·스타일을 보호하고 소유 항목/디자인/콘텐츠/고대비/Unload 변경 때 소유 색과 콜백을 해제한다. 체크는 기존 속성 콜백으로 현재 타일만 갱신하고, 새 루트가 로드되면 기존 관리 경로에 소유 항목을 다시 연결한다. 트리 선택색·글꼴 계열·크기·강조 관계는 변경하지 않았다. 실행 관측과 미확인 조건은 [실기기 기록](../../DEVICE-CHECKS.md#native-media)에 둔다.
