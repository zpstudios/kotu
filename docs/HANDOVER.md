## 2. 일하는 방식

**정본은 `CLAUDE.md`(협업 규칙·파이프라인·빌드 환경·브랜딩 불가침)** — 여기에는 CLAUDE.md에 없는
저장소 운용 세부만 둔다. CLAUDE.md와 어긋나면 CLAUDE.md가 이긴다(2026-08-21 개정: push는 **버전 커밋마다 즉시 1회**).

- **개발 우선순위: UI·코어 기능 우선**(사용자 확정). 녹화/녹음(A14·A15), HW 랭킹(A19), 포터블(A43),
  HWP 뷰어(A45)는 후순위.
- **push remote 이름 = `zp`**(`git push zp master`). 인증은 저장소 로컬 git 설정에 있음 — 401이면 사용자에게 토큰 재발급 요청.
- **CI 판정 정본 = release 워크플로**(실제 빌드·패키징을 하므로 초록 = 컴파일 통과 실증). build 워크플로가
  Actions 장애로 Queued/Startup failure여도 release가 초록이면 무해. 확인은 사용자 Chrome(브라우저 MCP)으로
  `github.com/zpstudios/kotu/actions`(최신 run의 `svg[aria-label]`이 성공/실패) — 활성 탭을 뺏지 말 것.
  build.yml·release.yml이 동시에 돌고 각 3~4분.
- **완료 처리 절차**: 항목을 `※ A?? 완료 — 결번`으로 바꾸고 부록 A 표에서 행을 빼며, 완료 상세는 미진행 항목이
  참조할 때만 본문에 남긴다(아니면 ARCHIVE로). 미구현 항목의 내용이 바뀌면 새 번호를 주지 않고 그 자리에서 갱신.
- **개인 실명·개인 메일 금지**(A82) — 실명을 지우는 작업의 기록에 실명을 인용하는 실수가 잦다(v0.90.0 실사례).

## 3. 반드시 알아야 할 함정

### 3.1 레거시 식별자 — 절대 일괄 치환하지 말 것
이름이 세 번 바뀌었다: `WinUtil`(초기 코드명) → `ZP`(v0.33.0) → `KOTU`(v0.86.0~).
**구 이름을 그대로 둬야 하는 곳**이 있다. 바꾸면 "구 등록 청소" 로직이 깨진다:

- `ExplorerIntegration.LegacyBrands = ["ZP", "WinUtil"]`
- `%AppData%\ZP`·`%AppData%\WinUtil`·`ZP-Main`·`WinUtil-Main`을 언급하는 주석
- `release.yml`의 구 packId 안내 문구

**교훈**: A46에서 "ZP" 문자열만 훑어 `%TEMP%\WinUtil\subtitles`를 놓쳤다(A64에서 발견).
리브랜딩 스캔은 **현재 이름이 아니라 모든 과거 이름으로** 해야 한다.

### 3.2 셸 등록은 "등록한 그 순간"으로 굳는다
`ExplorerIntegration`이 레지스트리에 쓰는 값 중 **exe 절대 경로와 표시 문구는 재등록될 때만 갱신**된다.
- 그래서 A52로 모듈명을 바꿔도 이미 켜 둔 사용자의 우클릭 메뉴는 옛 문구 그대로다.
- A64로 exe명이 바뀌면서 등록된 경로가 없는 파일을 가리키게 됐고, 실기기에서 실제로
  .png 더블클릭이 '어떤 앱으로 열까요' 팝업으로 빠졌다 → **v0.89.0의 A78이 자동 복구를 넣음**
  (매 실행 시 `ReRegisterIfExeMoved`가 경로 어긋남을 감지해 켜져 있는 등록만 조용히 재기록).
- **Capabilities와 UserChoice(A38)는 ProgID만 참조**해서 경로 변화의 영향을 받지 않는다.
- A38의 자체 검증(`VerifyUserChoice`)은 **우리 해시 알고리즘 기준의 자기일관성 검사**다 —
  Windows가 실제로 수용하는지는 열어 봐야 안다. OS가 알고리즘을 바꾸면 "전부 성공"으로 보이면서
  실제로는 전부 무효가 되는 맹점이 있다(§5 첫 항목의 의심 지점).

### 3.3 하드웨어 모듈은 거의 전부 static (프로세스 공유)
`HardwareModule`의 폴러·섹션 캐시·구독자 수·리프레시 주기가 모두 `static`이고,
센서 선택(A18)·주기(A29)도 프로세스 단위 설정 키다. **A42에서 의도한 설계**(드라이버 핸들·WMI 조회 공유)라
통째로 뒤집으면 안 된다. **A70(v0.131.0)이 그 분리선을 그었다** — 폴러·주기는 공유 유지, 선택(A18)·바
크기(A62)는 `HardwareInstanceState`(인스턴스 상태 + 전역 1벌 저장 깔때기)로 창별 분리. A60 3차의 창별
상태(피닝·순서·모드)는 **이 클래스에 필드를 얹는 방식**으로 간다(새 static을 만들지 말 것).

### 3.4 빌드를 실제로 깨뜨린 것들 (재발 방지)
- **csproj/XAML 주석 안에 하이픈 두 개(`--`)** → MSB4025로 빌드 실패. XML 주석 문법 제약.
  (A64에서 `--mainExe`를 주석에 적었다가 실제로 깨짐.)
- **PowerShell 백틱 줄바꿈 뒤에 주석** → continuation이 깨진다. 백틱은 그 줄의 마지막 문자여야 한다.
- `resources.pri` — unpackaged WinUI는 exe 옆의 **고정 이름 `resources.pri`** 만 찾는다.
  없으면 시작 시 `XamlParseException`으로 조용히 죽는다(v0.5.5~0.5.7에 실제로 겪음).
  `AssemblyName`을 바꾸면 `$(TargetName).pri` 폴백 이름도 따라 바뀌므로 `release.yml`을 같이 고쳐야 한다.
- **`FrameworkElement.Parent`를 "이미 추가했나" 가드로 쓰지 말 것** — 라이브 트리 부착 전
  (뷰 생성자 안)에는 `Children.Add` 뒤에도 Parent가 null이라, 같은 요소를 두 번 Add해
  `COMException 0x800F1000`으로 죽는다(v0.111.0/A62가 유발, v0.113.2에서 수정).
  중복 방지는 `Children.Contains`(또는 자체 플래그)로. 이것도 **CI·정적 검사로 못 잡는 부류**다.
- **XAML 요소를 다른 컨트롤로 옮겨 붙일 때(reparent)** 는 **반드시 옛 부모의 `Children`에서 먼저 제거**해야
  한다. 판정은 `Children.Contains`(위 항목과 같은 이유로 `Parent` 금지). 선례가 셋 있다 —
  `ImageViewerView.TakeBottomBar()`(v0.27.0), `ExplorerPane.DetachPathBar()`(A91/v0.115.0).
  ※ **x:Name 필드는 부모에서 떼어도 살아 있다**(`InitializeComponent`의 `Connect()`가 잡아 둔 참조).
  그래서 옮긴 요소의 이벤트 핸들러·코드비하인드 참조는 손댈 필요가 없다.
- **정적 이벤트 구독은 반드시 Unloaded에서 해제한다** — `CompositionTarget.Rendering`(A88/v0.114.0)처럼
  프레임워크 static 이벤트에 뷰 메서드를 걸면, 해제를 빠뜨렸을 때 **뷰와 그 창이 통째로 샌다**.
  이 저장소의 관용구는 `Loaded`에서 `-=` 후 `+=`(이중 구독 방지), `Unloaded`에서 `-=`다.
- **`{StaticResource Default*Style}` BasedOn 참조는 런타임에만 터진다** — v0.107.0의
  `DefaultDropDownButtonStyle`이 실기기 시작 크래시를 냈다(v0.113.1에서 수정). WinAppSDK 1.8이
  WinUI 컨트롤 기본 스타일을 지연 로딩해 App.xaml 파싱 시점에 키가 없다. **CI(컴파일)로는 못 잡고,
  정적 검사로도 못 잡는 부류** — 새 XAML에서 프레임워크 키를 StaticResource로 참조할 때는
  "그 키가 파싱 시점에 로드돼 있는가"를 의심할 것. 키 없이 setter만 둬도 기본 템플릿은 유지된다.
