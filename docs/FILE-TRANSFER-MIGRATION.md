# 구조 개선 2단계: 파일 복사·이동

2026-09-07 · v0.354.0 · A357 · `codex/architecture-document-session`

사용자가 2단계 진행과 필요시 서브 에이전트 위임을 지시했다. 기존 작업 브랜치를 이어서 사용하며
`master` 병합이나 정식 Release 발행은 하지 않는다.

## 구조와 범위

- `KOTU.App/ExplorerFileOps.cs`: 드래그·클립보드·충돌 대화상자·진행 안내를 연결한다.
- `KOTU.FileOperations/TransferPlan.cs`: 최상위 항목별 원본 트리와 파일 식별 정보를 먼저 읽는다.
- `KOTU.FileOperations/FileTransferService.cs`: 충돌 선택, 순차 실행, 취소 및 결과 집계를 담당한다.
- `KOTU.FileOperations/PhysicalTransferStore.cs`: 경로·파일 식별 검사, 이름 변경,
  임시 파일 복사·검증·반영 및 원본 정리를 담당하는 Windows 어댑터다.

새 프로젝트는 UI·다른 프로젝트·NuGet 패키지에 의존하지 않는다. Windows 파일 핸들을 사용하므로
실행과 파일시스템 테스트는 Windows에서 수행한다. 호출 API가 워커 실행을 보장한다.
이름변경·새 파일·새 폴더·휴지통·영구 삭제 및 드래그 기본 동작 판정은 이번 분리 범위 밖이다.

## 유지·강화한 계약

| 상황 | 동작 |
|---|---|
| 파일 충돌 | Replace / Skip / KeepBoth 및 작업 한 번에 한정한 모두 적용 |
| 폴더 충돌 | 대상 폴더를 지우지 않고 병합, 하위 폴더는 자동 병합, 하위 파일 충돌은 선택 |
| 같은 폴더로 이동 / 복사 | 이동은 건너뜀, 복사는 `(2)` 사본 |
| 숨김 파일·빈 하위 폴더 | 전송 대상에 포함 |
| 진행·결과 집계 | 최상위 항목 기준, 기존 UI의 3개 이상·100ms 표시 간격 유지 |
| 취소·항목 오류 | 완료된 결과 유지, 이후 작업 중단 또는 다른 최상위 항목 계속 |
| 대기 중 원본 교체 | 파일 ID와 변경 정보 검증으로 원본 삭제·잘못된 복사 거절 |
| 충돌 없는 동일 볼륨 이동 | 원본 핸들 기반의 덮어쓰기 없는 이름 변경. 다른 볼륨 오류일 때만 복사 방식으로 전환 |
| 복사 중 원본 변경 | 동일 원본 핸들로 읽고 쓰기·삭제 공유를 허용하지 않음 |
| 복사 결과 반영 | 대상 폴더 임시 파일에 기록·flush·SHA-256 검증 후 반영 |
| 복사 후 원본 삭제 | 반영된 대상의 파일 ID·해시를 확인하고 보호한 상태에서 원본 핸들로 삭제 |
| 파일의 추가 데이터 스트림 | 본문 외 스트림도 복사·해시 검증하고 원본 스트림 집합을 재검사 |
| 복사 방식의 이동 중 새 파일 유입 | 계획 밖 항목을 삭제하지 않음. 원본 폴더 정리는 비재귀이며 비어 있어야 함 |
| 연결 파일·폴더 및 연결 경로 | 재귀 순환·경로 우회를 막기 위해 실패로 처리 |
| 부분 이동·새 클립보드 내용 | 남은 원본이 있거나 클립보드 순번이 달라졌으면 잘라내기 목록을 비우지 않음 |

클립보드 비우기는 Windows 클립보드 잠금 안에서 순번을 비교하고 수행한다.
[GetClipboardSequenceNumber](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipboardsequencenumber)
및 기존 WinRT 입력을 연결한다. 핸들 이름 변경은
[FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)를 사용한다.

## 검증과 한계

신규 테스트는 실제 임시 파일·디렉터리·junction에서 정책, 원본/대상 변경, 파일 잠금,
취소, 연결 경로, 부분 이동을 확인한다. 테스트용 폴더 외 사용자 파일은 조작하지 않는다.
로컬 전체 솔루션 Release/x64 빌드 통과(경고 0·오류 0), 기존 테스트 249건 통과.
후속 경로·스트림 보완을 포함한 파일 전송 테스트 36건 통과(실패/건너뜀 0).
19개 프로젝트 참조·순환·UI 독립성·솔루션 매핑 정합성 검사 통과.
테스트는 Windows 권한이 필요한 파일 핸들·junction 검사를 위해 샌드박스 밖에서 실행했다.
[GitHub build 34122727973](https://github.com/zpstudios/kotu/actions/runs/34122727973) 전체 성공:
전체 빌드·테스트·배포 파일 검사·시작 검사·설치 EXE 생성·실제 설치·설치 파일 해시 비교·설치본 시작 통과.
검증 소스 커밋은 `8c7d181fadcb175ca5fc3272c4181271813ab99a`이며,
[설치 EXE 아티팩트](https://github.com/zpstudios/kotu/actions/runs/34122727973/artifacts/10019033020)에서
다운로드한다(14일 보관). 로컬 전달 위치는 `artifacts/installer-v0.354.0/KOTU-win-Setup.exe`다.
이후 문서만 추가한 결과 기록 커밋은 CI를 생략하며, 설치본 소스는 위 커밋과 같다.

서브 에이전트의 구현과 별도 독립 검토를 사용했다. 독립 검토에서 확인한 추가 스트림 유실과
EFS 암호화 해제 위험을 보완했다. EFS 보호는 API 계약과 코드 검토로 확인했으며 실제 암호화
파일 테스트는 수행하지 않았다. 긴 경로의 기본 이동과 복사 방식 이동은 실제 테스트로 확인했다.

이 작업은 여러 파일에 걸친 트랜잭션이나 실행 취소 기능을 추가하지 않는다. 일부 파일이 성공한 뒤
다른 파일이 실패할 수 있으며, 실패 후 원본과 대상 양쪽에 복사본이 남을 수 있다.
기존 파일 교체는 백업을 지정한다. 반영 이후 실패하면 `.kotu-backup-*.tmp` 및 남아 있는
`.kotu-transfer-*.tmp` 복구 파일을 보존하고 오류에 경로를 포함한다. 성공한 백업은 정리한다.
Windows ReplaceFile 정책에 따라 기존 대상에만 있던 추가 스트림과 보안 속성은 보존한다.
기존 대상 파일의 마지막 검사와 원자적 교체 사이에는 외부 프로세스의 변경 가능성이 남는다.
완전한 비교 후 교체 연산, 전원 장애 내구성, 네트워크 파일시스템의 로컬 NTFS와 동일한 동작을
보장하지 않는다. 파일 ID·크기·수정 시각을 모두 유지한 외부 변경까지 사전 계획이 감지하는 것도 아니다.
ReparsePoint 속성은 보수적으로 거절하므로 클라우드 자리 표시자도 제한될 수 있다.
EFS 암호화 파일의 복사 방식 전송은 암호화가 풀린 임시 파일을 만들지 않도록 사전 거절한다.
추가 스트림이 있는 폴더도 지원을 갖추기 전 원본 보호를 위해 계획 단계에서 거절한다.
이 제약은 일반 파일의 추가 스트림 복사 지원과 구분한다. 원본의 스트림 집합이 마지막 검사 직후
바뀌는 상황까지 원자적으로 묶는 파일시스템 트랜잭션은 제공하지 않는다.

수동 확인: 탐색기 세 표면의 드래그·Ctrl+X/V, 충돌 선택/모두 적용, 부분 이동 후 다시 붙여넣기,
이동 대기 중 다른 내용을 복사한 뒤 완료, 실제 다른 드라이브로 대용량 이동 및 취소 안내.

당시 다음 계획이었던 정식 배포의 테스트 필수화(3단계)는 완료했다. 이후 단계의 현재 상태는
[비동기·미디어 공통 정책 분리](ASYNC-MEDIA-MIGRATION.md)의 다섯 단계 표를 따른다.
