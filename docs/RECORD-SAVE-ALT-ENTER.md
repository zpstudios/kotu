## 녹화에서 확인한 현상과 수정

현재 배포 코드와 같은 녹화 모듈의 진단본에서 합성 문서 창을 무음 녹화했다. Stop이나 Close 입력 전에 약 8초 분량을 처리한 뒤 인코더 오류 `0xc00d4a3e`가 발생했다. 실패한 MP4는 10,559바이트이며 moov가 없었다. Dispose 뒤에도 파일 읽기가 공유 위반으로 실패했고, 읽기 전용 Restart Manager 조회에는 해당 검수 프로세스만 반환됐다. 녹화 창을 닫은 뒤에도 잠금이 유지됐으며 같은 프로세스의 마지막 합성 문서 창을 닫고 종료한 뒤 읽을 수 있었다. 특정 네이티브 핸들 소유자나 드라이버 결함까지 증명한 것은 아니다.

과거 미배포 B1b 후보의 `0xc00d36b5`와 이번 오류는 구분한다. 현재 원본에 그 후보를 합치거나, 이번 결과로 과거 실패가 해결됐다고 선언하지 않는다.

동일 진단본에서 `VideoEncoderOptions.IsHardwareEncodingEnabled = false`만 바꾼 비교본은 직접 Stop and save에 성공했다. UI 경과는 약 55초, MP4 메타데이터는 56.2초·영상 1트랙·음성 0트랙·moov 존재다. 파일은 459,175바이트이고 앱이 살아 있는 동안 SHA256 읽기에 성공했다. 진단 기록에도 완료 콜백·Dispose 반환·파일 열기·최종 이름 발행·저장 성공이 남았다. 이 결과는 직접 정지 경로이며, 닫기 후 저장 경로를 대신하지 않는다.

제품 변경은 기존 H.264 설정에 같은 옵션을 명시한 한 줄과 설명 주석이다. 30fps·고정 프레임·스로틀링·녹화 소스·콜백·Stop/Dispose·파일 발행 수명은 바꾸지 않았다. 공통 영상 설정이므로 화면·창·카메라 영상에 적용되며 마이크 전용 WAV는 대상이 아니다. 카메라와 음성 포함 녹화는 이번에 실행하지 않았다. 하드웨어 인코딩을 끄면 CPU·전력 사용량이 증가하고 고해상도 성능이 낮아질 수 있다. 작은 합성 창 시험으로 그 성능을 보장하지 않는다.

최종 비계측 Record 모듈에서도 새 프로세스 두 개로 시험했다. 직접 Stop and save는 저장 성공 표시와 304,163바이트·55.6333초 MP4를, 녹화 창 닫기 후 Stop and save는 창 정상 종료와 792,622바이트·55.8422초 MP4를 확인했다. 두 파일 모두 영상 1트랙·음성 0트랙·moov가 있으며 합성 문서 창이 살아 있는 동안 파일 해시를 읽었다. 실패본에서 보였던 저장 후 잠금은 이 두 성공 경로에서 재현되지 않았다.

초기 저장 수정 직후의 재생 검수는 미완료였다. 앱 내 재생은 준비 표시 후 검은 화면이었고, 별도 프레임 검증기는 두 파일 모두 EOF와 실제 픽셀 버퍼를 받았다. 닫기 후 저장 영상의 마지막 표본에는 의도한 합성 문서 창이 보였으나 직접 저장 영상의 처음·마지막 표본은 검었다. 각 파일의 네이티브 오류 5건은 내용이 보존되지 않았고 콜백 수와 MP4 샘플 수도 달라 전체 프레임의 정확성을 선언하지 않는다. 이 단계에서는 검은 화면의 캡처·인코딩·디코더 원인을 구분하지 못했다. 뒤의 검은 프레임 후속 수정에서 캡처 원인을 확인했다.

후속 시험에서는 합성 대상 창을 앞에 둔 채 직접 정지했다. 약72.13초·4,337,615바이트 MP4가 저장됐고 앱 생존 중 읽기에 성공했다. 입력 전달 시간 때문에 계획한65초 상한을 넘겼으며, 시작9.31초 후부터60.855초까지 앞에 보이는 대상을 관측한 뒤 녹화 창을 활성화해 정지했다. 처음부터 끝까지 같은 노출 조건인 대조 시험으로 표현하지 않는다.

세 파일을 같은 검증기로1배속 재생한 단일 후속 실행은 모두 EOF·정상 정지/해제·해시 보존을 확인했다. 추가 영상의 중간과 마지막 프레임에는 합성 문서가 보였고 초기210개 이후1,686개 버퍼가 비검정이었다. 앞선 직접 저장은1,669개 버퍼가 모두 검었고, 닫기 후 저장은 마지막 구간169개에 문서가 보였다. 세 파일 모두 동일한 변환기 생성 오류2건과 맨 위 표시 설정 오류3건이 기록돼 오류 메시지만으로 검은 결과의 원인을 구분할 수 없다. 콜백과 원본 샘플 수가 달라 정확한 전체 프레임 검증도 주장하지 않는다. 대상의 보임/렌더링 상태에 의존한다는 해석은 추론이며 가림이나 원격 연결을 원인으로 확정하지 않았다. 저장 완료 및 보이는 대상의 내용 증거는 확보했고, 모든 녹화 조건과 앱 내 재생 화면의 품질은 잔여 확인이다.

## 검은 프레임 후속 수정 — 원인 수정·제품 통합 검수 완료, 미배포

원본 프레임과 인코딩 직전 합성 화면을 따로 관측해 초기 검정이 디코더 이전에 생김을 확인했다. 수정 전 통제 실행은 첫 원본보다 먼저 검은 합성11개를 전달했고, 첫 원본은 약14초 후였다. 선택 창을 먼저 활성화하는 후보도 첫 합성1.453초·첫 원본21.754초로 실패해 제품 변경6파일을 되돌렸다. 이력을 삭제하거나 활성화만으로 해결됐다고 처리하지 않는다.

고정7.0.1 소스와 배포 PDB의 소스 체크섬을 대조했다. 첫 창 프레임은 크기 재설정 후 버릴 수 있는데, 빈 프레임 풀 분기가 기존 시간 초과·세션 재시작 처리를 건너뛰었다. 동시에 합성기는 첫 원본이 없어도 제한 시간이 지나면 초기 표면을 반환해 검은 영상이 저장됐다. 수정은 빈 풀도 기존 복구 처리를 거치게 하고, 실제 원본이 공유 표면에 처음 쓰이기 전에는 오디오·출력 파일·미디어 시계를 시작하지 않는다. 대기는 명목상5초이며 취소·실패를 확인한다. 기기/운영체제 호출 자체를 강제 종료하는 시간 제한은 아니다. 정상적인 검은 장면도 원본 쓰기만 있으면 허용하며, 첫 원본 이전의 최소화 대체 화면은 준비 완료로 보지 않는다. 화면 전용·카메라 시작 정책은 바꾸지 않는다.

수정 진단본은 대상 창을 다시 활성화하지 않은 상태에서 첫 원본0.817초·첫 합성1.104초를 받았다. 빈 풀→자동 재시작→실제 쓰기→초기 대기 종료도 기록됐다. 관측 원본55개·합성767개 중 검정0개이며27.38초 MP4 저장과 앱 생존 중 파일 읽기를 통과했다. 진단을 제거한 일반 엔진도 별도 프로세스의 문서를85.31초 녹화했고, 시작 후 약39초까지 대상을 활성화하지 않았다. 약70초에 대상을 최대화한 뒤에도 저장이 완료됐다.

저장된 두 영상은 재생 EOF와 정상 정리를 확인했다. 재생 관측은 각각730개·2,226개이며 검정은0개였다. 첫·중간·마지막 문서를 직접 확인했고, 마지막 영상은 최대화 이후 화면 변화도 보였다. 원본 MP4 샘플 수는662개·1,970개로 콜백 수와 다르므로 모든 원본 프레임이나 정확한 시각을 검증했다고 주장하지 않는다. 두 영상 모두 이전 검증기와 같은 변환/표시 오류5건을 남겨 검증기는 엄격 판정으로 종료1을 반환했다. 이 오류를 숨기거나 순수 무오류 재생으로 기록하지 않는다. 앱 자체의 Video 화면은 이번 추가 시도에서 메뉴가 열리지 않아 영상을 열지 못했으며, 파일 프레임 검증과 별개로 미확인이다. 재생기 제품 코드는 변경하지 않았다.

실제 수정 코드에서 추출한 제어 흐름17시험이 통과했고 공개 API908행은 원래 패키지와 동일하다. 일반·진단 엔진을 모두 빌드했으며 수정 파일의 경고는0개다. 수정하지 않은 외부 원본2곳의 경고는 기록해 보존했다. 고정 소스·패치·라이선스·재현 가능한 빌드와 App/Record/CI 연결을 구현했다. 과거 엔진 주입은 차단하고 엔진 누락·오래된 소스·해시/참조/게시물 불일치·라이선스 누락을 검사한다. 잘못된 입력을 거부하는11시험을 통과했다. 전체 Release/x64 빌드는 경고0·오류0, 전체 자동 시험은8어셈블리1,206/1,206(실패·미실행0), 일반 self-contained win-x64 로컬 publish도 통과했다. App/Record의 실제 참조와 게시 DLL·원본 라이선스 해시가 수정 엔진과 일치하며 공개 API908행도 동일하다. CI 연결은 구성했고 원격 CI·설치 패키지·공개 배포는 실행하지 않았다. 최종 제품 엔진의 UI는 다시 실행하지 않았으며, 실제 녹화 검수본과 기능 소스가 같고 빌드 경로·오류 기록용 소스 이름만 다름을 대조했다. 빌드 중 두 헤더의 오류 기록용 이름에만 #line을 붙이며 원본 바이트와 줄 번호를 보존한다. 기능 변경은 고정 소스의3파일뿐이다. 엔진의 기존 경고2건과 관리 앱 빌드0경고는 구분한다. 근거는 로컬 `artifacts/record-black-frames-20261110/main-review/native-acceptance.json`, `native-controlled.json`, `final-cross-process.json`, `frame-validation`이다.

## Alt+Enter 동작과 안내

기존 코드의 일반 Monaco 편집기에서 Alt+Enter가 줄바꿈과 수정 상태를 만들고 전체화면을 전환하지 않는 현상을 실제로 확인했다. Undo로 문서를 원상 복구하고 시험 파일의 해시가 변하지 않은 것도 확인했다.

수정본은 편집기가 소유한 정확한 Alt+Enter만 전용 메시지로 전달하고 기본 줄바꿈을 막는다. 셸은 첫 keydown에서 기존 전체화면 전환을 한 번 실행한다. 반복 입력은 소비하며, 평범한 Enter와 다른 modifier 조합은 기존 편집기로 넘긴다. 네이티브 텍스트 편집과 찾기/바꾸기 입력, All Readable 안의 문서에도 입력 소유권을 연결했다.

초점·IME 조합·팝업·이름 변경·파일 선택 화면·작업 화면·문서 교체/분리·저장 전환 상태를 확인한다. 이미 전달 중이던 요청도 원래 편집기와 중간 소유자가 계속 유효해야 실행한다. WebView 이벤트와 네이티브 이벤트가 같은 키를 중복 처리하지 않게 분리했다. 사용자 가이드는 현재의 전체화면 2상태 전환과 독립 패널 동작으로 정리했다. 실제 IME·키 길게 누르기·모든 팝업 조합을 시험했다고 주장하지 않는다.

최종 일반 검수본의 Monaco와 네이티브 대체 편집기에서 실제 Alt+Enter로 709×535→2560×1080→709×535 왕복과 선택 문자열 보존·개행 없음·수정 표시 없음을 확인했다. Monaco의 평범한 Enter는 편집되고 Undo 뒤 원문·선택·깨끗한 수정 상태로 복구됐다. 네이티브 편집기의 파일 선택 화면에서는 Alt+Enter가 전체화면을 전환하지 않았다. 찾기 입력의 왕복도 앞선 실행에서 확인했다.

앞선 Monaco 실행 한 번은 키를 소비했지만 전환하지 않았다. 뒤의 관측본은 모든 초점·수명 검사를 통과해 각 방향을 한 번 전환했고, 동일한 일반 검수본을 다시 준비한 후에도 왕복에 성공했다. 최초 무반응의 원인은 확정하지 않았으며 이 근거로 초점 보호 조건을 느슨하게 바꾸지 않았다. 최종 성공과 최초 미해결 관측을 함께 보존한다.

## 저장·Alt+Enter 단계의 검증과 남은 확인
