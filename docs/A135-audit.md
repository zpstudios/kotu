# A135 감사표 — F1/F2 사이드바·오버레이 동작 전 모듈 일관성 (2026-08-18)

> **성격**: A110 스타일 코드 시뮬레이션 감사의 단일 원본(A94-matrix 선례).
> 배경 = 실기기 보고(2026-08-16): 비디오·이미지·PDF 등 **콘텐츠 열림 상태**에서 F1/F2 on/off가
> 안 듣는 모듈이 있다. 이 문서가 전수 특정의 결과이고, **수리는 0건**(코드로 확정된 불통 칸 없음 —
> 남은 후보는 전부 실기기 판별, §4).

판정 파이프라인(모듈 공통 — 셸 단일 경로):
1. **도달**: `RootLayout.AddHandler(KeyDownEvent, …, handledEventsToo:true)` — `MainWindow.xaml.cs:205`
   (KeyUp은 206). XAML 트리 안 어디에 포커스가 있든, 다른 핸들러가 Handled를 걸었든 셸이 받는다.
   따라서 코드 층에서 도달이 끊기는 경우는 "포커스가 XAML 트리 밖/없음"뿐 = 실기기 판별.
2. **선소비 양보**: `OnOverlaySideKey`(1663)의 `e.Handled` 검사(1665) — 트리 전체에서 F1/F2에
   Handled를 거는 코드는 탐색기 표면 F2 이름변경 2곳뿐(전수 grep, §3-ⓑⓓ).
3. **게이트**: `HasPanelContext`(1473) = 파일 열림 ∨ 빈 파일 모듈(1432) ∨ 패널 제공 뷰(1466).
4. **전이**: `OnOverlaySideDown`(1699) → `ApplyOverlayStates`(2095) 단일 종착점.

**수리 0건.** 코드로 확정된 불통 칸이 없다(ⓐⓑⓓ 부존재, ⓒ는 실기기 판별 지시). 버전 무변경.

## §4 — 실기기 확인 포인트 (ⓒ 정황 증거 포함)

① **포커스 고아 가설(이번 보고의 최유력 정합)**: 포커스가 패널 안에 있는 채로 그 패널이 닫히는
   경로가 4개다 — F1/F2 열림 1회 닫기·2연타 해제(첫 탭)·Enter 일괄 닫기·경계 버튼. 이때
   `Hide()`(FileListOverlay 176·ContentInfoOverlay 57·SidePanelHost)는 Visibility만 내리고
   **포커스를 아무 데도 되돌리지 않는다** — 셸의 완화장치는 S4 종료 한 곳뿐
   (`ExitOpenFileBrowsing` 끝의 `(ModuleHost.Content as Control)?.Focus(...)`, 2409행).
   collapse된 요소의 포커스를 WinUI가 어디로 옮기는지(null이면 이후 셸 KeyDown 자체가 미발화 =
   F1/F2 전멸)는 런타임 몫. **중앙이 클릭-포커스 불가 표면인 모듈(비디오·오디오 스왑체인,
   이미지·PDF 비트맵)은 클릭으로도 복구가 안 되고, 문서-텍스트는 에디터 클릭으로 복구된다** —
   "비디오·이미지·PDF에서만 안 듣더라"는 보고 패턴과 정합. 재현 절차: 콘텐츠 열림 → F1 2연타
   (좌 사이드바) → 리스트 클릭(포커스 진입) → F1(닫힘) → **F1 재누름이 듣는가**.
② **전체화면 진입 직후**: 하단 바가 통째로 Collapsed(생성자 AppWindow.Changed, 249~256행) —
   하단 바 버튼으로 진입했다면 포커스 소유 버튼이 사라진다(①과 같은 고아 유형).
③ **libvlc VideoView**: LibVLCSharp.WinUI 3.10.0(SwapChainPanel 템플릿 컨트롤). 자식 HWND
   생성·포커스 탈취 여부는 코드로 확정 불가. 정황: VideoSurface 클릭은 Tapped만 있고 Focus 호출
   없음 — 클릭으로 포커스가 스왑체인에 "들어가는" XAML 경로는 없다(들어간다면 네이티브 층).
④ **Fn 잠금/OEM 키보드**: F1이 OS 도움말·미디어 키로 먹히는 기종(HANDOVER 기존 등재 항목).
⑤ **전체화면·스왑체인 위 반투명 렌더**(표 1의 `*`): v0.156.0(A129) 기존 실기기 항목과 동일 묶음.
⑥ ①이 실기기에서 확정되면 수리 방향(차기 항목 등재용): Hide 직전 "포커스가 이 패널 안인가"
   판정(`IsFocusWithin` 1930 재사용) 후 2409행과 같은 모듈 뷰 재포커스 — 단일 종착점
   `ApplyOverlayStates` 안에서. 전역 훅·새 상태 불요.

## 2차 방어 수리 (2026-08-18 — ⑥의 선제 적용)

- **수리 지점**: `ApplyOverlayStates` 말미 한 블록(MainWindow.xaml.cs — UpdateEdgeButtons 뒤).
  닫힘 경로 전부가 이 메서드를 지나므로 분산 대입 없음. 훅·새 전역 상태 없음.
- **조건**: 4표면(ListOverlay·InfoOverlay·LeftPanelHost·RightPanelHost) 각각
  `!IsOpen && IsFocusWithin(표면)` — 즉 "화면에 없는 패널 안에 포커스가 남은" 경우에만
  `(ModuleHost.Content as Control)?.Focus(Programmatic)`(2409행과 같은 관용구·같은 대상).
  열려 있는 패널 안 포커스는 무개입(리스트 타이핑 탐색 유지). 실패는 조용히 무시.
- **실기기 판별 잔여**: ⓐ 이 수리는 `FocusManager.GetFocusedElement`가 collapse된 요소를
  계속 가리키는 형태의 고아만 잡는다 — WinUI가 포커스를 **null로 떨어뜨리는** 형태라면
  판정 자체가 불성립(§4-①의 "null이면 KeyDown 미발화" 갈래)이라 증상이 남는다 →
  그 경우 가설 재조사(포커스 널 갈래·②③④ 후보). ⓑ 재현 절차는 §4-① 그대로 —
  콘텐츠 열림 → F1 2연타 → 리스트 클릭 → F1 닫기 → F1 재누름이 듣는지.
