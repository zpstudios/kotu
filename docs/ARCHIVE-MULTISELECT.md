# 압축 선택 목록과 명시적 폴더 해제 — A367~A369

2026-09-18 사용자가 원인 조사 후 수정을 승인했다. v0.363.0 로컬 구현과 독립 검토를 완료했다. 전체 Release/x64 빌드 경고·오류 0(15.68초), 8개 시험 프로젝트 404/404 통과다. GitHub CI·배포는 대기 중이며 실제 Windows 탐색기 메뉴 및 WinUI 조작은 아직 검증하지 않았다.

## 확인한 원인

- A367: 기존 자동 해제는 압축 **내부 최상위 항목**이 하나면 래퍼 폴더를 생략한다. 선택한 압축 파일 수와는 다른 조건이다. 자동 정책은 유지하고 `--extract-to-folder`와 명시적인 새 폴더 해제 메뉴를 추가한다.
- A368: 종전 실행 요청은 첫 경로만 보존했고 모듈 진입도 단일 경로 배열을 생성했다. Windows 정적 메뉴도 `%1` 입력이었다. 반면 모듈의 다중 파일 선택창은 전체 목록을 전달했다. 내장 탐색기의 기존 좌측·타일 우클릭에는 압축 명령 자체가 없었다.
- A369: 단일 경로 경계 외에도 압축 목록 조회·옵션 입력 중에는 아직 앱 작업 ID가 없었다. 재전달 요청이 같은 Archive 창을 재사용하면 앞선 화면이 교체되어 준비 단계가 중단될 수 있었다.

제보 이미지의 실행 버전·탐색기 종류를 확정한 것은 아니다. 위 내용은 현행 코드에서 확인한 손실 경계다.

## 수정 경계

`LaunchRequest.Paths`와 `OpenContext.InputPaths`는 선택 목록을 복사해서 보존한다. 기존 단일 `FilePath`와 생성 경로는 호환한다. 압축 원본 폴더도 동사 진입에서 허용하며, 없어져 버린 선택 원본은 나머지만 조용히 압축하지 않고 실패로 표시한다.

Windows 탐색기는 `IExecuteCommand`·`IObjectWithSelection` COM 경계에서 선택 배열을 받는다. 한 번의 Execute를 하나의 nonce 전달 파일과 요청으로 연결한다. 시간 간격으로 요청을 합치거나 `%*` 치환이 전체 선택을 보장한다고 가정하지 않는다. 첫 실행과 AppInstance 재전달 모두 같은 비동기 전달 파일 해석을 거친다. 잘못된 전달 파일은 요청 실행 없이 일반 오류를 알린다.

압축 생성은 전체 원본 목록을 한 번의 옵션 입력과 생성 작업으로 넘긴다. 각 동사 요청은 새 목적 창을 사용해 앞선 옵션 입력이나 목록 준비 화면을 교체하지 않는다. 일반 파일 열기의 창 재사용 정책은 유지한다.

다중 해제는 `BackgroundJobService.StartMany`로 선택한 압축마다 작업을 **전부 원자적으로 등록한 뒤** 실행한다. 목록 조회·암호 요청·폴더 결정도 작업 내부에서 수행한다. 한 압축의 실패나 암호 대기는 나머지 작업을 지우지 않는다. 화면은 자기 작업 목록 중 진행 중인 ID를 소유자로 제공하므로 마지막 활성 작업까지 기존 전환 보호가 유지된다. 화면 Cancel은 그 선택 묶음을 취소하고 공용 Jobs는 개별 취소를 제공한다.

실제 결과 위치가 결정되면 `BackgroundJobContext.SetResultPath`가 잠금 안에서 스냅샷을 갱신하고 잠금 밖에서 알린다. 완료된 기록은 후속 갱신으로 바뀌지 않는다. 결과 열기는 실제 파일·폴더 위치를 사용한다.

## 충돌·암호·취소

자동 해제의 기존 단일 루트 정책과 `(2)`, `(3)` 이름 회피는 유지한다. 강제 폴더 해제는 내부 항목 수와 관계없이 래퍼 폴더를 선택한다. 프로세스 전역 예약 집합과 실제 파일·폴더 존재 검사를 함께 사용해 동시에 계획하는 작업이 같은 결과 경로를 잡지 않게 한다. 압축 생성도 같은 대상에 진행 중인 다른 작업이 있으면 실패한다.

예약은 **KOTU 프로세스 내부**의 작업 충돌을 막는다. 다른 프로세스가 동시에 출력 경로를 만드는 상황까지 원자적으로 차단한다고 보장하지 않는다. 기존 사용자가 고른 Extract to 대상·명시적 덮어쓰기 정책과 백엔드 경로 처리 정책은 유지한다. 빈 폴더 보존 확대는 이번 범위가 아니다.

암호는 작업별 요청 ID로 전달하고 스냅샷에 저장하지 않는다. 취소는 협조적이며 현재 파일 처리를 기다릴 수 있다. 이미 만든 결과는 자동 삭제하지 않는다. 활성/암호 대기/취소 중 작업의 앱 종료 방지는 기존 공용 작업 서비스와 동일하다.
